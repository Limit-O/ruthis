# 提交规范

## 核心原则：没有实现一个确切目标，就不要 commit

- 一次 commit 必须对应一个**完整、自洽、可构建**的目标：一个功能、一个修复、
  一次重构、一批文档。"目标完成"的判断标准：此刻构建通过、功能可用、
  不需要"后面再补"才能工作；
- 开发中的断点交给 `--dev` 热重载和编辑器本地历史，**不要拿 commit 当存档**；
- WIP 提交会把坏状态永久写进历史——此后任何人 bisect、回溯、检出都会踩进去。
  工作区可以乱，历史必须干净；
- 实在需要暂存破碎思路时，用 `git stash` 或开分支，不进 main。

## 信息格式

```
<类型>：<一句话说清做了什么、为什么>

<可选正文：要点列表，补充动机与取舍>
```

- 类型取：`功能` / `修复` / `重构` / `文档` / `构建` / `清理`；
- 标题具体、可检索：写「修复音量滑条高度为零不可见」，不写「修复 bug」；
- 涉及设计决策的，注明文档出处（如 docs/z-axis.md §3）或一句话点明理由；
- **禁止** IDE 自动生成的提交信息（「修改： xxx / 新文件： xxx」）——那等于没写。

## 历史整理

- push 之前，本地历史随时可以整理：琐碎提交 `git reset --soft` 压扁、
  不合格信息 rebase 改写——push 前是最后的整理窗口；
- 整理完成后必须校验 `git diff 旧基准 新主线` 为空：**只动历史，不动内容**；
- 已 push、已共享的历史一律不改写（本地领先远端的提交除外）。
